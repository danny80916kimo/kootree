# 將模擬通報存入 Supabase

此方案以現有第一筆 `tree_reports` 的欄位與通報類型作為原型，在獨立的 `public.dashboard_demo_reports` 產生 200 筆資料。樹木 UUID 直接取自 Supabase 的行道樹，不再使用本機 CSV 樹號。

每筆都有 `is_simulated=true`、`simulation_batch` 與「【模擬資料】」文字。使用者、照片與實際通報內容不會被複製。額外的風險分數為虛構，沒有診斷效力。這份 SQL 不會改動真實通報、樹籍或工單，也不會觸發正式通報流程。

## 執行

1. 請有建表權限的管理員進入專案 `pxglzzlihfhdjulegxag` 的 SQL Editor。
2. 貼上同資料夾的 `seed_dashboard_demo.sql`，確認專案後執行。
3. 結果應顯示 200 筆：待確認 80、已確認 80、已排除 40。已確認不代表已結案。

腳本在同一交易中建表並產生資料，失敗會回滾；同一批次再次執行不會新增重複筆數。API 公開角色只有這張模擬表的讀取權限，不能寫入；後續異動仍由管理員處理。只公開無使用者身分與照片的模擬紀錄。

## 後台接入

後台提供「真實／模擬」切換，分別讀取 `tree_reports` 及 `dashboard_demo_reports`，不會把兩個來源合併。模擬資料已匯入時，初始顯示模擬模式並保留明確標示；模擬風險分數僅在模擬模式顯示。月份物候規則屬於另一種資料，這批模擬通報不包含物候規則。

目前沒有直接 PostgreSQL 連線或可執行 DDL 的 Supabase 管理工具，本機未直接執行這份 SQL；管理員執行後，已於 2026-10-24 透過公開 API 確認模擬表可讀、共 200 筆，並驗證模擬標記。
